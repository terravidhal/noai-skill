# Report — the ledger and `RAPPORT.md`

The report is the proof. It must let a reader check three things without trusting
the agent:

1. the before and after scores are real and comparable;
2. each pass changed something measurable;
3. what remains, and why.

## Files

```
trueline/
  before.json          scan before the first edit
  after.json           scan after the last pass (with --compare)
  passes.json          ledger written by the agent during the passes
  report.json          machine-readable summary generated by report.mjs
                       (`input` = original, `afterInput` = corrected screen)
before.png / after.png optional screenshots of the same viewport and theme
RAPPORT.md             human report at the project root (or as asked)
```

Add `trueline/` to the project's `.gitignore` unless the user wants the evidence
committed. `<skill>` in the commands is the folder that contains `SKILL.md`; run
them from the project root.

## Scan commands

```bash
# 1. before, same viewport and theme for every run
node <skill>/scripts/scan.mjs <target> --theme light --width 1440 --height 900 \
  --json trueline/before.json

# 2. after every pass (append the real number to the ledger)
node <skill>/scripts/scan.mjs <target> --theme light --width 1440 --height 900 \
  --compare trueline/before.json --json trueline/step-3.json

# 3. final, with a finish line
node <skill>/scripts/scan.mjs <target> --theme light --width 1440 --height 900 \
  --compare trueline/before.json --json trueline/after.json --max-slop 20
```

A comparison across different rubrics exits 3. Do not work around it by deleting
the old file; re-scan the before on the installed rubric and say that you did.

## Ledger schema

`passes.json` is a JSON array or `{ "passes": [...] }`. Only `pass`, `changes`
and the change fields are required; `scoreAfter` and `delta` are filled only when
a real scan was run after that pass.

```json
{
  "skill": "trueline",
  "rubric": "1",
  "screen": "Orbit workspace overview",
  "passes": [
    {
      "pass": "2. Colour and depth",
      "category": "color",
      "scoreAfter": 41,
      "delta": -12,
      "changes": [
        {
          "file": "app/globals.css",
          "selector": ".hero",
          "before": "linear-gradient(135deg, #7c3aed, #2563eb)",
          "after": "background: #f7f4ee",
          "signal": "A1"
        }
      ]
    }
  ]
}
```

Rules for an honest ledger:

- `signal` is the id the change targets (`A1`, `B1`, `D1`, …). One change can
  support a signal without being the only fix.
- `before` and `after` are the actual values, short and copy-pastable. Not "made
  it cleaner".
- `file` is the real path. `selector` is the real selector or a short DOM path.
- `scoreAfter` only if the scanner actually ran after that pass. Otherwise omit
  it; the report prints `—`.
- Never invent a per-pass score to make the table look better.

## Generate

```bash
node <skill>/scripts/report.mjs \
  --before trueline/before.json \
  --after trueline/after.json \
  --passes trueline/passes.json \
  --out RAPPORT.md \
  --json trueline/report.json \
  --title "trueline — <screen>"
```

`report.mjs` also accepts `--after` without `compare`; it computes the delta from
the two scan files. It never runs a scan itself.

## Markdown shape

The generated report contains, in this order:

1. title, the before and after paths, mode, rubric, confidence;
2. before / after / change table;
3. category table with max, before, after and delta;
4. per-pass table: pass, category, edits, score after, delta, with a note when a
   pass has no separate scan;
5. per-edit table: pass, signal, file, selector, before, after;
6. signals removed, with the selector that carried them;
7. signals remaining, with penalty and evidence;
8. waivers, with reason;
9. comparison warnings (for example a signal that disappeared into
   `display:none`);
10. verification checklist;
11. the command to reproduce the scan.

## What to add by hand

The generator cannot know these, so add them to the report when relevant:

- which files were changed, if the ledger is partial;
- commands run (build, typecheck, lint) and their result;
- what could not be verified (no running app, no dark theme, no mobile build);
- any waiver the user requested, with the date and the approver;
- a short note on the direction, if the user asked for one.

## Good and bad evidence

**Good**

- `A1 · body · linear-gradient(135deg, #7c3aed, #2563eb) → #f6f7f9`
- `B1 · .grid-3 · three 300×180 cards with the same structure → metrics strip +
  wide chart + narrow list`
- `E1 · .lede · #9ca3af on #ffffff, 2.5:1 → #5e554a, 6.1:1`

**Bad**

- "Improved the colours and spacing."
- "The page feels much more premium now."
- "Reduced slop" with no number and no selector.

## When the score does not fall

Say it. List the remaining signals. Do not:

- rescore with a different rubric, viewport, theme or mode;
- hide the element or the section that carries the signal;
- add a waiver without a reason and the user's agreement;
- change the example or the weights to make the number smaller.

A run that ends with "the score did not move; here is what is left" is a valid
and useful result.
